### ADR-005. Маршрутизация обращений: fine-tuned RuBERT on-prem


Статус: на рассмотрении
Дата: 2026-11-25
Инициатива: №5. Маршрутизация входящих обращений по нужным отделам





###### Контекст

Кол-центр RetailBank обрабатывает 30–50 тысяч обращений в месяц через чат, e-mail и телефон. Оператор L1 вручную читает обращение, определяет тему и переводит в нужный отдел. Среднее время обработки — 2–3 минуты. Около 15–20 процентов обращений попадают не в тот отдел с первого раза, что приводит к повторному переводу, потере 5–10 минут и снижению CSAT.



Цель инициативы — автоматически классифицировать текст обращения и назначать отдел-исполнитель за менее чем 1 секунду. При уверенности ниже 0,6 — отправлять на общую очередь для ручного назначения оператором L1.



Из паспорта инициативы: тип задачи — многоклассовая классификация текста. Модальность — текст. Выход модели — softmax-вероятности по 5–8 классам отделов. Бизнес-выход — название отдела или fallback на общую очередь. Источник правильного ответа — история CRM с меткой отдела, назначенного оператором.



###### Решение по данным

* Источник данных: История обращений из CRM за последние 12 месяцев. Поля: текст обращения, канал, время, сегмент клиента, назначенный отдел.
* Разметка: Целевая метка — поле «отдел-исполнитель» в тикете CRM. Если CRM логировала переводы — берётся последний отдел, в который было направлено обращение. Если поле пустое — запись исключается из обучения.
* Золотая выборка: Дополнительно формируется контрольная выборка из 1000 обращений, размеченных тремя опытными операторами по мажоритарному голосованию. Используется для валидации качества модели и аудита согласованности.
* Обработка ПДн: Тексты обращений могут содержать ФИО, телефон, e-mail клиента. Перед передачей в модель все ПДн удаляются регулярными выражениями и NER-моделью. Обезличенные тексты хранятся в DWH в отдельной схеме, доступной только для обучения модели.
* Правовое основание: Обработка обезличенных текстов для внутренней классификации не требует уведомления субъекта, так как не является автоматизированным решением, затрагивающим права клиента. Если используется внешняя LLM — требуется договор с обработчиком и подтверждение локализации данных в РФ.
* Допущения: История CRM содержит корректные метки отдела в не менее 80 процентах записей. Если метки некорректны — качество модели упадёт, потребуется ручная разметка 10 тысяч обращений для переобучения.



Решение по размещению
On-prem в периметре банка. Модель RuBERT небольшого размера (300 миллионов параметров) не требует GPU для инференса — CPU inference занимает около 50 миллисекунд. Размещение на существующих CPU-серверах банка без дополнительных закупок.



Для пилота: Один CPU-контейнер в Kubernetes банка. Ресурсы: 2 vCPU, 4 GB RAM. Latency около 50–100 миллисекунд, throughput до 100 запросов в секунду. Этого достаточно для пиковой нагрузки 10 запросов в секунду.

Для target-продукта: Два CPU-контейнера для отказоустойчивости. Ресурсы: 4 vCPU, 8 GB RAM на каждый. Redis для кэширования частых запросов. Мониторинг latency, throughput и fallback rate.



Допущения. Существующая Kubernetes-инфраструктура банка имеет свободные ресурсы для размещения контейнеров. Если свободных ресурсов нет — потребуется докупка CPU-сервера за 300 тысяч рублей.



###### Решение по модели

Fine-tuned RuBERT. Модель семейства BERT, дообученная на русском языке. Размер — 300 миллионов параметров, что достаточно для классификации текстов на 5–8 классов. Fine-tuning на истории обращений банка занимает 2–4 часа на одной GPU (можно арендовать или использовать GPU-сервер инициативы №1 в нерабочее время).

Обоснование: 

LLM (Qwen, Llama) дают избыточную точность для задачи классификации на 5–8 классов. RuBERT работает на CPU, latency 50 миллисекунд против 200–500 миллисекунд у LLM. Fine-tuning RuBERT на 10 тысячах примеров занимает 2–4 часа, а не 2–3 дня для LLM. RuBERT не требует GPU для инференса, что снижает TCO.

TF-IDF не учитывает порядок слов и контекст. Для обращений с неоднозначными формулировками («хочу закрыть карту» — техподдержка или претензии) контекст критичен. RuBERT даёт прирост accuracy на 5–10 процентов относительно TF-IDF.



**Архитектура инференса**: Предобработка текста: удаление ПДн, приведение к нижнему регистру, токенизация. Прогон через RuBERT, получение эмбеддинга CLS-token. Прогон через классификационную голову (linear layer) — получение softmax-вероятностей. Выбор класса с максимальной вероятностью. Если максимальная вероятность ниже 0,6 — fallback на общую очередь.

**Дообучение**: Еженедельное дообучение на новых размеченных обращениях из feedback loop (вердикты операторов L1 по fallback-обращениям). Полный retrain — раз в месяц. Версионирование модели в MLflow Registry.

**Допущения**: Точность RuBERT на золотой выборке будет не ниже 90 процентов. Если точность ниже — переходим на LLM-каскад (Qwen2.5-7B, размещение на GPU с инициативы №1). Если точность LLM также ниже 90 процентов — задача не решается ML, возврат к ручной маршрутизации.



###### Триггеры пересмотра

* Рост fallback rate выше 15 процентов. Если модель слишком часто отправляет обращения на общую очередь, операторы L1 не разгружаются. Триггер: fallback rate выше 15 процентов в течение недели. Действие: переобучение с изменением порога уверенности с 0,6 до 0,5 или смена модели на LLM.
* Падение accuracy ниже 85 процентов на золотой выборке. Триггер: accuracy ниже 85 процентов по результатам weekly-теста. Действие: аудит золотой выборки на предмет дрейфа тем обращений, переобучение на свежих данных, при повторном падении — переход на LLM.
* Появление нового канала обращений. Если банк запускает новый канал (например, мессенджер) — распределение тем и стиль текста могут измениться. Триггер: accuracy по новому каналу ниже 70 процентов после месяца накопления данных. Действие: дообучение модели с добавлением признака канала.
* Изменение рубрикатора отделов. Если банк меняет структуру отделов (объединяет претензии и возвраты) — модель нужно переобучать с нуля. Триггер: изменение числа классов. Действие: полный retrain на новой разметке, A/B-тест до переключения.
* Жалобы комплаенс на качество маршрутизации. Если комплаенс фиксирует систематические ошибки по определённому отделу. Триггер: accuracy по отделу ниже 75 процентов в течение месяца. Действие: аудит обучающей выборки по этому отделу, oversampling редких тем.
* Отказ оборудования. Если CPU-сервер, на котором работает RuBERT, выходит из строя. Триггер: недоступность модели более 1 часа. Действие: временный переход на LLM-каскад (GPU с инициативы №1), восстановление CPU-сервера в течение 24 часов.
